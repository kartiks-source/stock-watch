# Security

How Catalys modules keep secrets and access safe. Covers `modules/stock-watch` (the web app on Railway) and `modules/stock-watch-sheets` (the Google Sheet). Rules that apply everywhere: AGENTS.md rules 7 (no secrets in git, ever) and 8 (Shopify is read-only). Decisions: ADR-0001 (Shopify keys in Key Vault, read-only), ADR-0011 (auth model). Operations: `docs/RUNBOOK.md`.

Found a problem? Tell the repo owner directly (not in a public issue or a shared channel), with steps to reproduce.

## Secrets: what, where, how to rotate

| Secret | What it unlocks | Lives in | Rotate |
|---|---|---|---|
| `ADMIN_PASSWORD` | the whole web app: every page, every `/api` route, Clear, the ingest key, exports | Railway variable (service `web`) | Change the variable and apply it (Railway redeploys). Every session is signed out (the cookie key includes a fingerprint of it). In production it must be 12+ characters or the app won't start. Tell the team the new one by a private channel, never in chat history, a doc or a sheet |
| `VIEW_PASSWORD` (optional) | a view-only sign-in: every page, number and CSV; no write (`POST/PUT/PATCH/DELETE /api/*` → 403), no ingest key, no backup export | Railway variable (service `web`) | Change or remove the variable and apply it: every view session is signed out (a fingerprint of it is inside the signed view cookie). Must differ from `ADMIN_PASSWORD`; the app refuses to start with it set but no `ADMIN_PASSWORD` |
| Per-store passwords (SW-062, ADR-0016) | one person's sign-in: only the stores the owner ticked, as admin (that store's settings, Mark ordered, backup export…) or viewer (read-only) | `DATA_DIR/access.json` on the volume (mode 600): scrypt hashes only (N 16384, r 8, p 1, 16-byte salt); the password is shown once to the owner on the Data page and never stored, logged or sent again | Data → People → **New password** (the old one and every session made with it stop working at once) or **Remove** (signs them out everywhere). Change `ADMIN_PASSWORD` to sign everyone out |
| Session key `DATA_DIR/secret` | signing the `sw_session` cookie (with a fingerprint of `ADMIN_PASSWORD`) | the `/data` volume, mode 600; made on first start | Delete the file and restart: a new one is made and everyone is signed out |
| `PERFORMITY_POC_API_KEY` (alias `TOKEN_API_KEY`), with `PERFORMITY_POC_API_URL` (alias `TOKEN_API_URL`) and optional `PERFORMITY_BRAND_ID` (`PERFORMITY_ORIGIN` is not a secret: our domain, sent as `Origin`) | asking Performity's POC API for a fresh read-only Shopify token for the brand(s) our key is allowed (option A, ADR-0014). Sent only as the `X-Api-Key` header, only from our allow-listed outbound IP, and only when the URL is `https://` (or `http://localhost` / `127.0.0.1` for the stand-in) and the key is set: otherwise no call is made at all, the brand list included | Railway variables (service `web`); the URL and brand ID are not secret but live beside the key | Ask Performity for a new key (one-time link), set the variable (Railway redeploys), check the Data page shows a good pull, then ask them to revoke the old one. A wrong key pauses pulls 15 minutes locally, so we never trip Performity's 5-wrong-keys IP block. Delete `PERFORMITY_POC_API_URL` to stop pulling at once |
| Shopify access tokens from Performity | read access to the store for one pull | process memory only, for that pull (asked again before every pull, never written to disk or logs) | Nothing to rotate on our side: revoking our API key stops new ones |
| Shopify client ID + client secret | read access to the store's products, inventory and orders (`read_products`, `read_inventory`, `read_orders`) | Azure Key Vault: `shopify-<store>-client-id` and `shopify-<store>-client-secret` (or one `shopify-<store>` JSON secret). Stop-gap: Railway variables `SHOPIFY_CLIENT_ID`, `SHOPIFY_CLIENT_SECRET` | The brand rotates the secret in its Shopify Dev Dashboard → update the Key Vault secret (or variable) → restart the app (credentials are cached 30 minutes, the 24-hour Shopify token until near expiry). Check the Data page shows a good pull |
| Legacy `SHOPIFY_ACCESS_TOKEN` (`shpat_…`) | same as above | Railway variable | Revoke in Shopify admin (uninstall the custom app or regenerate), set the new one, restart. Prefer moving to client ID + secret |
| Azure service principal: `AZURE_TENANT_ID`, `AZURE_CLIENT_ID`, `AZURE_CLIENT_SECRET` (+ `AZURE_KEY_VAULT_URL`) | reading Shopify secrets from the vault | Railway variables | Create a new client secret in Azure (Entra ID → App registrations → the app → Certificates & secrets), set the variable, restart, check a pull works, then delete the old secret. Give the principal **Get** on secrets only |
| Ingest key | posting stock and order rows to `/ingest/stock` and `/ingest/order` (Shopify Flow) | `store.json` on the `/data` volume (settings), shown masked on the Data page (admin only); also inside every backup and export | Data page → Shopify Flow → **New key**, then update the `X-Ingest-Key` header (or `?key=`) in both Flows straight away: rows sent with the old key are refused (401) |
| Session cookie `sw_session` | being signed in for 30 days (admin, or view with `.view.` in the value) | the browser; signed with HMAC-SHA256 under a key made from the random secret in `DATA_DIR/secret` (mode 600, made on first start) plus a fingerprint of `ADMIN_PASSWORD` (`server.js` `keyOf`) | Change `ADMIN_PASSWORD` (signs everyone out; `VIEW_PASSWORD` signs view sessions out), or delete `/data/secret` and restart (signs everyone out, a new secret is made). Never copy `secret` off the volume |
| Store cookie `sw_store` (not a secret) | nothing: it only names the store the page opens when the address has no `?store=` | the browser; set by the store picker, readable by the page (not HttpOnly), a year | Nothing to rotate. The server takes it only if it is a valid id **and** in the store list (else the first store); it never grants access |
| Morning digest webhooks: `DIGEST_WEBHOOK_URL`, `DIGEST_WEBHOOK_URL_<ROLE>` (e.g. `_CEO`) | posting into the receiving chat / Zapier / Make flow; these URLs usually carry a token, and the digest carries sales numbers | Railway variables only (the page can't set one: `PUT /api/digest/settings` refuses a `webhookUrl` with 400; it shows only the host; never logged, never in `store.json`; LOGIC.md §17) | Make a new incoming-webhook URL in the receiving tool, set the variable, apply, press **Send now** on Data → Morning digest to check, then delete the old webhook in that tool. Point each one only at a channel the role's people may read |
| Sync alert webhook: `ALERT_WEBHOOK_URL` (optional) | posting into the team channel that gets "Shopify pulls failing / working again" (the URL usually carries the channel's token; no keys or tokens are ever in the message) | Railway variable only; https only (other URLs are ignored) | Same as the digest webhooks: new URL in the tool (Slack / Google Chat), set the variable, apply, delete the old one |
| Google Sheet "Publish to web" CSV links | anyone with the link can read the Stock log / Order log tabs | Data page settings (`store.json`) and the brand's Google account | In the Sheet: File → Share → Publish to web → stop publishing, publish again, paste the new links on the Data page |
| Backups and exports (`/data/backups/*.json`, `GET /api/export/backup.json`) | all sales data, Mark-ordered records and decisions (`sideFiles`) **and the ingest key** | the volume; wherever someone saved a download | Treat a leaked export as a leaked ingest key: rotate it. Delete downloads when done; never commit, attach or paste them |

Never put any of these in code, Markdown, logs, commit messages, chat or a Google Sheet. Before every commit, run the secret check in `docs/DEFINITION-OF-DONE.md` on the staged diff and read every hit: a real value (not a variable name or a placeholder) means stop and remove it.

## Auth model (today)

- **One shared admin password** (`ADMIN_PASSWORD`, ADR-0011). The sign-in page (`POST /login`) sets an HttpOnly, SameSite=Lax cookie valid 30 days (`Secure` behind HTTPS), signed with a key made from the random `DATA_DIR/secret` plus a password fingerprint (SW-008), so changing the password signs everyone out. Scripts can use HTTP Basic auth with any user name. Sign out is `POST /logout` only (a link elsewhere can't sign you out).
- **Refuses to start** (exit 1, nothing served) with `NODE_ENV=production` and `ADMIN_PASSWORD` missing or under 12 characters; with Shopify connected and no `ADMIN_PASSWORD`; and with `VIEW_PASSWORD` set but no `ADMIN_PASSWORD`, or the two equal. Only a local run (not production, no Shopify) without `ADMIN_PASSWORD` is open, for development.
- **Login attempts:** one limiter covers the sign-in form and Basic auth (SW-008): 10 wrong passwords per IP per 15 minutes, then 429 without checking. The IP is the last `X-Forwarded-For` hop (the one Railway's proxy adds; earlier hops are whatever the client sent), else the socket. Across all IPs, 100 wrong passwords per 15 minutes switch every new attempt to "password still checked, a wrong one gets 429": the cap slows a spread-out guesser without letting a stranger lock the owner out (critic round 1, SEC-1). The per-IP map is swept and capped at 10,000 entries.
- **`/health`** is open and returns `{"ok":true}` plus the app version and the build's short commit SHA, or 503 with the save/load error. **`/status`** (uptime monitors) is open: version + SHA, freshness, row counts, store size, capacity warnings and `writing` (SW-055); no names, keys or error text. A second copy on the same `DATA_DIR` refuses every write with 503 (`src/lock.js`). Version and SHA are public on purpose (SW-056: check the live build after a deploy); the SHA is kept only when it is 7–40 hex characters (`src/version.js`), so `BUILD_SHA` can't put anything else on an open page.
- **Outbound calls** carry no key of ours except to Performity: alert and digest webhooks are POSTed as JSON (https only; digest also allows `http://localhost`), never follow redirects, time out after 10 s, and alert text has tokens scrubbed. A webhook that fails never breaks a pull.
- **Writes from another site** are refused (403) before any route: `Sec-Fetch-Site` must be same-origin (or `Origin` must match the host) on every `POST/PUT/PATCH/DELETE` to `/api/*`, `/login`, `/logout` (SW-016). Security headers on every answer: CSP (`script-src 'self'`; `img-src 'self' data: blob: https://cdn.shopify.com`, 1.4.0: product pictures from Shopify's CDN only), `nosniff`, `no-referrer`, `frame-ancestors 'none'`, `X-Frame-Options: DENY`, HSTS behind HTTPS.
- **Logs** (SW-054, `src/log.js`): one JSON line each; every line is scrubbed of Shopify tokens (`shpat_`, `shpca_`, `shppa_`, `shpss_`), `Bearer` values, `X-Api-Key` values and `key=` / `password=` values before it is written. The request line per API call has method, path, status, time and store only: never the query string, a header or a cookie. The boot line lists which variables are set (true/false), never a value.
- **Flow ingest** is not behind the login; it's protected by the ingest key alone, sent in the `X-Ingest-Key` header (`?key=` still accepted, warned in the log at most hourly: it ends up in proxy logs), at most 500 rows per request (413, SW-009); refused with 409 once Shopify is connected (ADR-0009). Bad input anywhere → 400 with a plain message, never a stack (SW-018). CSV downloads guard formula cells (SW-017).
- **Shopify is read-only in code:** every call goes through `assertReadOnly()` (`src/gql-guard.js`, SW-051), a small GraphQL tokeniser: comments, strings and block strings are whole tokens (a `#` or `mutation` inside one can't hide or fake anything), and every top-level definition must be a `query` (or the `{` shorthand) or a fragment beside one; mutations, subscriptions, type definitions, unclosed strings, unbalanced brackets and stray tokens are refused before anything is sent. The app asks only for read scopes, because a shared key may carry write scopes. No webhooks are registered.
- **Token permissions** (SW-051, `src/token-scopes.js`): each pull first reads `currentAppInstallation { accessScopes { handle } }`. A token from one of our own apps (Key Vault or Railway variables) that also has any `write_*` scope is refused: the pull stops with a plain error asking the brand to remove the write permissions (and a token whose scopes can't be read is refused too). Performity's token (ADR-0014) is not refused, since their app needs write scopes for its own work: Data shows "Token also allows writes; this app only reads" and the server logs it once per store (scope names only, never the token).
- **The Google Sheet** never talks to Shopify and holds no key: Shopify Flow writes rows into it with the brand's own Google connection.
- **View-only password** (`VIEW_PASSWORD`, SW-029, LOGIC.md §13): one gate right after sign-in refuses every write to `/api` with 403 before any route runs (Mark ordered, decisions, settings, import, clear, demo, pulls, digest settings and send-now included). `GET /api/export/backup.json` is admin-only. Same wrong-password limiter as admin.
- **Several stores** (ADR-0015): `ADMIN_PASSWORD` and `VIEW_PASSWORD` are for every store (anyone signed in with them can open any listed store; view-only is read-only on all of them). A store id comes only from `?store=` or the `sw_store` cookie and must be a uuid or `^[a-z0-9][a-z0-9-]{0,60}$` **and** in the store list, else 404 before any file is touched; it is the whole folder name under `DATA_DIR/stores/`, so no path can leave it. Each store has its own Flow ingest key (`/ingest/*?store=<id>`); one store's key never writes to another. `/status` stays free of store names and ids.
- **Per-store people** (SW-062, ADR-0016, `src/people.js`): only the owner (`ADMIN_PASSWORD`, no person) sees Data → People and `/api/people` (everyone else 403). A person's password is `<id>-<20 random chars>` (120 random bits), stored as an scrypt hash in `DATA_DIR/access.json`; the id prefix finds the one hash to check, so a sign-in costs one scrypt. Same sign-in form, Basic auth and wrong-password limiter as the main passwords. Their cookie is `exp.p.<id>.<gen>.sig` (signed with the same session key); it is checked against `access.json` on every request, so removing a person or giving a new password (gen + 1) ends their sessions at once, and a role or store change applies on their next request. Every store-scoped route checks the store: `?store=` outside their list → 403 (also for ids that don't exist, so ids can't be probed); without `?store=`, a `sw_store` cookie on another store falls back to their first store; `GET /api/stores` lists only theirs; digest and exports are store routes, so the same rule covers them. A viewer person gets the same 403 on every write and on the backup export as `VIEW_PASSWORD`. The change log names the person. A broken `access.json` turns per-store sign-ins off (logged) and is never written over. Logs carry the person id, never the name or password.

## Endpoints that change or wipe data

Each also answers at `/api/v1/…` with exactly the same checks (SW-050: the path is rewritten before routing, after the cross-site check). All need the admin login except `/ingest/*`; a `VIEW_PASSWORD` session gets 403 on every one. Each acts on one store only: the one named by `?store=<id>` (else the `sw_store` cookie, else the first store). Each wipe of `store.json` is backed up first (`docs/RUNBOOK.md`); backups, the export and restore carry `onorder.json`, `decisions.json` and `suppliers.json` as `sideFiles` (SW-005, SW-040). Full request and response shapes: `modules/stock-watch/API.md`.

| Endpoint | Effect | Undo |
|---|---|---|
| `POST /api/clear` | deletes every stock change and order line, every Mark-ordered record and every slow-seller decision (409 while a pull runs) | restore the `…-before-clear.json` backup: it carries `onorder.json` and `decisions.json` too (`sideFiles`, RUNBOOK → Restore) |
| `POST /api/demo` | replaces all data with demo data and forgets Decide decisions (refused while Shopify is connected, and 409 while the store holds real data: Clear first; the page asks to confirm) | restore the `…-before-demo.json` backup |
| `POST /api/import?kind=stock\|order` | adds CSV rows (duplicates skipped; 409 with Shopify connected or a pull running). On a demo store the demo rows and demo decisions go first. With `&map=` it also saves the column mapping to `mappings.json` (header names only, no row data; SW-045). `POST /api/import/preview` writes nothing but is admin-only and same-site checked like every POST | restore a backup from before the import |
| `PUT /api/settings` | planning settings, store name, Sheet links; `newIngestKey: true` rotates the ingest key (breaks Flow until updated); every change logged (who, old → new; the key masked) | set the old values again; a rotated key can't be brought back |
| `POST /api/onorder` | Mark ordered: stores or removes (qty 0) PO records `{qty, eta, at, by}` in `onorder.json`, at most 500 per request; ordered lines leave Order today | post the same IDs with `qty: 0` (or `clear: true`), or remove it in the product drawer; mark again with the old quantity and date; restore a backup (`sideFiles`) |
| `POST /api/decide` | stores or removes (empty decision) a slow-seller decision (keep / drop / clear) in `decisions.json`; the item is hidden until its sales change | **Undo** under the table, or post the same `id` with `decision: null`; restore a backup (`sideFiles`) |
| `PUT /api/suppliers`, `POST /api/suppliers/map`, `POST /api/suppliers/import` | supplier terms (lead time, MOQ, case pack) and SKU → supplier in `suppliers.json` (SW-040); change order quantities and lead times on Reorder; every change in the settings change log; same admin + same-site gate as every `/api` write | put the old values back (the change log has them); restore a backup (`sideFiles`) |
| `POST /api/targets` | sets or removes (amount 0) a monthly sales target for one group in `targets.json` (SW-042); who and when are kept | post the old amount again, or 0; restore a backup (`sideFiles`) |
| `POST /api/lists` | saves (by name, replacing a list of the same name) or deletes (`delete: true`) a saved product list in `lists.json` (SW-044), shared by the team | save it again from the pasted list; restore a backup (`sideFiles`) |
| `PUT /api/digest/settings` | morning digest hour, roles, paused (webhook URLs are env only: a body with one → 400) | set the old values again |
| `POST /api/digest/send` | posts the digest (sales numbers) to the configured webhook now, logged | — (a sent message can't be recalled; check who the webhook reaches) |
| `POST /api/people`, `PUT /api/people/<id>`, `POST /api/people/<id>/reset`, `DELETE /api/people/<id>` (owner only, SW-062) | add a person (password shown once), change their name / role / stores, give a new password (old one and its sessions end), remove (signs them out); `DATA_DIR/access.json`, previous copy kept as `access.json.bak` | add them again / give a new password; or copy `access.json.bak` over `access.json` and restart |
| `POST /api/sync`, `POST /api/shopify/sync` | fetch new rows from the Sheet links / Shopify now (a first Shopify pull on a demo store clears the demo) | — |
| `POST /api/shopify/year` (admin only, 1.4.0) | replaces the store's `year.json` days it reads with Shopify's own daily sales and stock-change totals (ShopifyQL, read-only through the same guard; needs `read_reports`; up to 60 reads, queued like a pull) | run it again (it is only Shopify's reports) |
| `POST /api/shopify/history` (admin only, SW-063) | replaces the store's `src: 'rebuilt'` stock rows with a fresh rebuild from Shopify's change log (ShopifyQL, read-only through the same guard; needs `read_reports`) | run it again; restore a backup |
| `POST /ingest/stock`, `POST /ingest/order` | add rows (ingest key, no login) | restore a backup; rotate the key if misused |
| `GET /api/export/backup.json` (admin only), `GET /api/export/reorder.csv` | read-only downloads (the backup includes the ingest key) | — |

Sheet sync (SW-052, `src/sheet-fetch.js`): the typed link must be `https://docs.google.com/…`; redirects are followed by hand, at most 3, only to https `docs.google.com` or `*.googleusercontent.com` (no other host, http, user:password@ or port); the body is capped at 20 MB and the whole fetch at 20 s. The link is never put in an error or log.

**Container (SW-053):** the base image is pinned by digest; the app runs as `node`, not root: `scripts/entrypoint.sh` starts as root (`RAILWAY_RUN_UID=0`) only to hand the root-owned volume to `node` once, then drops privileges with `su-exec` (docs/RUNBOOK.md, Container user).
